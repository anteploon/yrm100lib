# Taste
- Prefers deliverables materialized as real files in the repo rather than only presented as chat answers — applies both to config/ops artifacts (like service units, with accompanying docs) and to analysis output (e.g., code-review findings written to `review.md`). Confidence: 0.6
- Expects technical claims/instructions (especially in generated docs) to be verified against the actual environment/hardware rather than asserted from assumption, and will push back when they don't hold. Confidence: 0.6
- Prefers empirical, hands-on diagnosis: wants the agent to actually run/reproduce the failing and working cases in the current environment ("you can try it yourself") and to use available system diagnostic tools (e.g. strace) rather than reason from theory alone. Confidence: 0.6
- Pushes back on proposed changes that would remove empirically-required hardware workarounds (e.g., an inter-command delay added because real RFID modules misbehaved); expects such workarounds to be preserved unless replaced by something demonstrably safe, not merely theoretically cleaner. Confidence: 0.55
- Prefers a read-only scoping pass before edits: when diagnosing a fix, wants an inventory of exactly which functions/files would need to change (with locations) and explicitly asks for no code changes. Confidence: 0.5
- When investigating a bug or behavior, wants a detailed step-by-step walkthrough of the exact code path (with file:line references and why each branch is/ isn't taken), not a high-level summary. Confidence: 0.5
- Wants commit messages in imperative mood with a short descriptive subject line plus a body explaining the problem being fixed (e.g., "Fix CI to use existing make targets" followed by why the old targets didn't exist). Confidence: 0.5
- Expects bug fixes to be accompanied by a regression test that asserts the corrected behavior (e.g., explicitly requests "add a regression test"). Confidence: 0.55
- After a code change, expects the work to be validated by compiling the project and running the real binaries against the actual hardware devices (explicitly naming the runtime invocations to check), not just by passing unit tests. Confidence: 0.5
